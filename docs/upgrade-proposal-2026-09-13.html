iML Markdown Editor 升级方案

日期：2026-09-13　·　基于代码全量分析与本轮重构后的现状 定位：纯粹的 Markdown 编辑器，用于记笔记，附带轻量、可离线的 AI 辅助

一、现状一句话

本轮已把 v1.9 的公众号写作工作站整体拆掉，产品回到"编辑器本体"。现在的骨架是：Electron 主进程（文件 / AI 请求 / 图片生成）+ React 渲染层（Zustand 单 store、Tiptap 富文本、CodeMirror 源码），代码量从约 15,000 行降到约 10,700 行，类型检查与构建全绿。

本轮顺手修掉的问题（细节见 README 版本历史）：双击 .md 不显示、子目录文件把工作区挪走、关标签 / 新建文档丢文件树、重启丢未保存内容、⌘E / ⌘⇧S / ⌘H 快捷键冲突、Dock 图标偏大、查找替换只有壳、大文档每次按键整篇转换等。

下面按"值不值得做"排序给方案，每项标了预估工作量：S（1~2 天）、M（一周内）、L（两周以上）、XL（独立立项）。

二、编辑器本体：让"写"这件事更顺手

这是定位的核心，优先级最高。

# 功能 为什么值得 量级
1 斜杠命令菜单（非 AI） 行首 / 目前只唤起 AI 气泡。Notion 式的 /表格 /代码块 /图片 /公式 菜单是现代编辑器的基本预期，也能把工具栏进一步收起来 S
2 Callout / 提示块 记笔记高频需求：> [!NOTE] > [!WARNING] 这类 GitHub 风格提示块，富文本模式渲染成彩色卡片 S
3 自动目录（TOC）与标题编号 长笔记必备。[TOC] 占位符自动生成；侧边栏目录支持折叠层级 S
4 粘贴智能化 粘贴 HTML 自动转 Markdown；粘贴 URL 自动取网页标题变成链接；粘贴图片压缩后存 assets/（现在原样存，一张截图几 MB） M
5 图片与附件管理 图片相对路径、重命名、删除时清理孤儿文件；插入 PDF / 文件附件 M
6 表格增强 列宽拖拽记忆、对齐写回 Markdown、CSV 粘贴成表 M
7 源码模式滚动同步 左右两栏现在各滚各的，改成按行映射同步滚动 S
8 大文档性能 现在富文本每次编辑都整篇 HTML → Markdown（已防抖到 150ms）。真正的解法是增量转换：只序列化变化的顶层块。万字以上笔记会明显受益 L
9 专注写作 打字机滚动（当前行居中）、无干扰全屏、字数目标进度、段落高亮 S
10 主题与排版自定义 正文字体、行距、页宽可调；导出 PDF 时套用同一套主题；增加几套阅读主题 M
11 拼写检查与自动补全 Electron 内置拼写检查开关；源码模式补全 Markdown 语法与文内标题链接 S
12 导出格式 现在只有 PDF。加 HTML（单文件、内联图片）、DOCX（docx 库）、图片长图 M

三、笔记能力：从"编辑器"变成"笔记本"

定位是记笔记，这一层决定用户愿不愿意长期留下来。

# 功能 说明 量级
1 统一"笔记库"模型 现在"工作区"和"笔记"是两套概念（文件树按打开的文件自动切换根目录；笔记库只列顶层 .md）。建议合并：一个笔记库 = 一个根目录，侧边栏就是这棵树，支持子文件夹、收藏、最近。这是"目录和文件关系不对"的根本解法，本轮只是止血 M
2 全文搜索 跨文件搜索是笔记工具的命门。方案：主进程用 SQLite FTS5（better-sqlite3）建索引，监听目录变化增量更新；渲染层 ⌘⇧F 打开结果面板 M
3 双向链接与反链 [[笔记名]] 语法、自动补全、反向链接面板、未创建链接点击即建。记笔记从"文件夹"进化到"网络"的关键一步 M
4 标签 #标签 内联识别，侧边栏标签视图，点击筛选 S
5 每日笔记与模板 ⌘⇧D 打开今天的日记；新建文档可选模板（会议、读书、周计划） S
6 快速捕获 全局快捷键呼出菜单栏小窗，随手记一条追加到收件箱笔记 M
7 版本历史 每次保存留本地快照（.iml/history/），可对比、回滚；有 Git 仓库时可选自动提交 M
8 文件监听 外部（同步盘、其他编辑器）改了文件时自动刷新，避免覆盖 S

四、轻量 AI：本地优先，可关，不打断

# 功能 说明 量级
1 内置本地推理运行时 ✅ 26.1 已实现「本机模型」：不打包 node-llama-cpp，而是按平台下载 llama.cpp 官方发布的 llama-server（约 11 MB）放进应用数据目录，由主进程托管进程；推荐清单含讯飞星火 X2.5 1.7B / 4B、面壁 MiniCPM5 1B / 2B、Qwen3-4B 的 GGUF，按本机内存 / 核心数标注是否满足，断点续传 + SHA256 校验，可导入自己的 GGUF。后续可加：按机器自动推荐量化档位、Windows 上 CUDA / Vulkan 变体的运行时 L

五、iPad 端 + 手写 + 多端同步（远期，独立立项）

这是你提到的 GoodNotes 方向。先说结论：值得做，但它不是 Electron 项目的延伸，而是第二个产品。

5.1 现实约束

  • Electron 无法运行在 iPadOS。iPad 端必须是原生应用（Swift + SwiftUI），手写用 PencilKit，这是 Apple Pencil 体验最好、成本最低的路线。跨端框架（Flutter 等）的手写延迟和压感都不如 PencilKit。
  • 两端共享的不是代码，而是文件格式和同步规则。所以第一步是把格式定死。

5.2 建议的文件格式

  • 正文仍是纯 Markdown（note.md），保证任何编辑器都能打开。
  • 手写作为旁挂图层存在同名文件里：note.ink.json（PencilKit PKDrawing 序列化）+ 一份 note.ink.svg 渲染快照。Mac 端先做只读叠加显示，iPad 端可编辑。
  • 手写与正文的锚定用"段落 id + 相对偏移"，避免正文改动后笔迹漂移。

5.3 同步方案

  • iCloud Drive：文件级同步，不需要自己写服务器。Mac 端只需允许把笔记库根目录设在 ~/Library/Mobile Documents/iCloud~... 或任意 iCloud 目录；iPad 端用 UIDocument / 文件协调器。这是最快能跑通的路径。
  • 其他云盘：百度网盘没有面向第三方的实时同步 API，只能靠其客户端的"同步空间"目录间接实现，体验取决于百度客户端。通用方案是 WebDAV（坚果云、Nextcloud、群晖、阿里云盘 WebDAV 桥接都支持），建议把 WebDAV 作为"其他云盘"的统一接口，百度网盘归入"目录同步"这一类。
  • 冲突：文件级同步必然有冲突。规则建议：Markdown 按段落三方合并，合并不了就生成 note (冲突副本).md；手写图层以时间戳新者为准并保留旧副本。

5.4 分阶段路线

  1. Mac 端：笔记库支持放在 iCloud Drive / 同步盘目录，加文件监听与冲突副本处理（本项目内可做，M）。
  2. iPad 端 v0：只读阅读器 + 目录浏览（Swift 新项目，L）。
  3. iPad 端 v1：手写批注图层，Mac 端只读渲染（L）。
  4. iPad 端 v2：正文编辑（可用 Down / MarkdownUI 等 Swift 库），完整双向协同（XL）。

八、需要你拍板的几个决策

  1. 富文本模式要不要保留双模，还是走 Typora 式的"单一混合模式"？ 双模的 HTML ↔ Markdown 往返是很多历史 bug 的来源；混合模式实现难度高但体验统一。建议 2.x 先保留双模，把往返做扎实。
  2. AI 气泡要不要缩减到"文本 + 流程图"两种模式？（四.4）
  3. 笔记库合并工作区（三.1）会改变现有使用习惯，是否接受？
  4. iPad 端何时启动：建议里程碑 2 之后，先把格式（5.2）定下来再动手。
  5. 版本号：本次重构建议直接发 2.0.0，README 与更新检查都按新主版本走。
